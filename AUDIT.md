## 2. Go-бэкенд (`go/cmd/nekobox_core/happ/`)

- Алгоритм — точный порт эталона `happ-decrypt-universal/lib.rs`: порядок префиксов,
  base64 std/urlsafe с автопаддингом, байтовые шафлы `m4831f/inverseM4831f/m4842j/permute4`
  (взаимоуничтожающаяся пара m4831f→inverse сохранена как в эталоне), разбор crypt5
  (marker = первые4+последние4, nonce 12 байт, длина сегмента из ведущих цифр,
  разделитель `f`, RSA→ChaCha20-Poly1305), неизвестный/отсутствующий префикс → crypt5.
- Криптография: stdlib `crypto/rsa` (PKCS#1 v1.5) + `crypto/x509` (PKCS#8);
  `chacha20poly1305` из уже имевшейся в графе зависимостей `golang.org/x/crypto v0.23.0`.
- Ключи — публичные данные из `Happ-converter` (assets/*.json, go:embed), идентичность
  ключам эталонного Rust-бинарника доказана прогоном 38 векторов (см. ниже).
- CLI `nekobox_core happ-decrypt`: единственная строка JSON на stdout (`{ok,result|error}`),
  exit 0/1; баннер версии в этом режиме подавлен, в остальных режимах поведение байт-в-байт
  как в апстриме.
- Конкурентность: `sync.Once` на загрузку ключей, `Decrypt` stateless; потокобезопасно.
- Обработка мусора на входе: ошибки возвращаются, паники исключены (негативные тесты).

### Тесты (`go test ./happ/ -v`, и локально, и в CI)
- `TestVerifiedVectors` — 38 векторов, каждый заранее сверен с официальным бинарником
  `happ-decrypt-universal v1.0.0 (windows-x64_x86.exe)`: результаты идентичны 38/38.
  Покрывают 4 RSA-режима и все 34 маркера crypt5.
- `TestSyntheticAllKeys` — генерация «с нуля» для каждого из 4 нативных ключей и всех
  34 crypt5-ключей (конструкция как в эталонных тестах lib.rs).
- `TestRoundTripShuffles`, `TestInvalidInputs`, `TestUppercasePrefix` — самоинверсия
  перестановок, мусор на входе без паник, регистр префикса.
- `go vet ./happ/` — чисто; `gofmt` применён.

## 3. C++ GUI

- `main/HappLink.{hpp,cpp}` — запуск `nekobox_core happ-decrypt` отдельным короткоживущим
  процессом: таймауты 3 с (старт) / 10 с (завершение), kill при зависании, строгое
  повторное использование уже существующего пути бинаря рядом с GUI
  (`applicationDirPath/nekobox_core.exe`); stdout парсится как JSON (SeparateChannels,
  stderr игнорируется); все ошибки — человекочитаемые и переводимые строки.
- Хук в `GroupUpdater::AsyncUpdate` — стоит ДО всех существующих веток, поэтому
  `happ://`-ссылка физически не может попасть в старую логику; для не-happ ввода
  поведение функции не изменилось (условие просто не срабатывает).
- Дешифровка выполняется в фоновом потоке (`runOnNewThread`), все UI-действия
  (предупреждение, лог, рекурсивный `AsyncUpdate`) — через `runOnUiThread`.
  На ошибке вызывается `finish` (подписочные обновления не зависают).
  `MW_show_log` защищён проверкой на пустой std::function.
- Диалог `DialogHappDecrypt` — кодом, без .ui; расшифровка синхронно с WaitCursor
  (явное действие пользователя, типично <0.5 с); «Добавить в NekoBox» отдаёт результат
  штатному `groupUpdater->AsyncUpdate` (подписка → стандартный диалог выбора, ссылки →
  штатный импорт профилей) и закрывает окно; «Скопировать» — в буфер обмена.
- Автоподключение слота по имени `on_menu_happ_decrypt_triggered` ↔ action
  `menu_happ_decrypt` (соглашение uic); AUTOMOC/AUTOUIC включены в проекте — Q_OBJECT
  диалога покрывается moc.
- Переводы: `ru_RU.ts` — контексты MainWindow (пункт меню), DialogHappDecrypt (окно),
  QObject (ядро + хук); все source-строки совпадают с tr()-вызовами байт-в-байт;
  XML валиден. Английский текст показывается в остальных локалях (стандартное
  поведение Qt).
- `.ui` и `.ts` проверены XML-парсером; CMake — только добавление файлов, настройки
  сборки не менялись.

## 4. Не-регрессия

Все точки касания существующего кода — ранние return-ветки и добавления в списки:
старые сценарии (буфер обмена с обычными ссылками, QR, подписки, TUN, системный

## 5. Известные ограничения (не ошибки)

1. Декриптор знает только опубликованные наборы ключей (4 RSA + 34 маркера crypt5).
   Если Happ добавит новые ключи после снимка reference-репозиториев — такие ссылки
   дадут понятную ошибку «unknown crypt5 key marker».
2. Успешная расшифровка не гарантирует успешную загрузку подписки: часть провайдеров
   проверяет заголовки (X-Hwid, X-Real-Ip и т.п.) при скачивании. Это ограничение
   формата, а не кода.
3. Сборка не подписана сертификатом — антивирусы могут показывать стандартное
   предупреждение при первом запуске.
